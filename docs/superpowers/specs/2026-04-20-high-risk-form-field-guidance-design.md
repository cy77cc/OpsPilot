# 高风险表单字段聚焦说明卡设计

日期：2026-04-20  
状态：已确认（待实现计划）

## 1. 背景

OpsPilot 当前前端表单大量依赖以下几种方式传达填写要求：

- 字段标签（label）
- 占位文案（placeholder）
- 必填校验与提交失败提示
- 个别页面零散的 `extra` / `tooltip`

这种方式对普通字段足够，但对“新手第一次看不懂、填错代价高、专业性强”的字段明显不够。用户往往要先试填、再报错、再来问“这个字段到底填什么”，导致以下体验问题：

- 第一次填写时频繁中断，依赖口头说明或开发协助。
- 复杂表单提交失败后才知道字段含义，排障路径长。
- 同类字段在不同页面提示方式不一致，学习成本无法复用。

当前问题在以下页面最典型：

- `web/src/pages/Deployment/Infrastructure/ClusterImportWizard.tsx`
  - `kubeconfig`、`endpoint`、`ca_cert`、`cert`、`key`、`token`
- `web/src/pages/Monitor/ChannelsConfigPage.tsx`
  - `channelProvider`、`channelTarget`、`channelConfigJson`
- `web/src/pages/Settings/AIModelSettingsPage.tsx`
  - `provider`、`model`、`base_url`、`api_key`、`temperature`

这些字段的共同点是：表面上只是输入框，实际上承载认证、连接、路由、模型调用等专业语义；如果没有前置解释，用户很难在聚焦的当下理解“这里应该填什么、这个值是干嘛的、填错会怎样”。

## 2. 目标与范围

### 2.1 目标

- 让第一次填写复杂表单的用户，在聚焦专业字段时基本不需要额外询问“这个字段是什么意思”。
- 降低因误解字段用途或格式而导致的提交失败、连接失败、认证失败。
- 在不重写现有表单体系的前提下，建立统一、可扩展的高风险字段说明模式。

### 2.2 首发范围

- 前端新增统一的“字段聚焦说明卡”交互能力。
- 首发只支持中文说明文案。
- 首发仅覆盖专业性强、填错代价高的字段，不覆盖普通字段。
- 首批落地以下代表页：
  - `web/src/pages/Deployment/Infrastructure/ClusterImportWizard.tsx`
  - `web/src/pages/Monitor/ChannelsConfigPage.tsx`
  - `web/src/pages/Settings/AIModelSettingsPage.tsx`

### 2.3 非目标

- 首发不为所有字段统一加提示。
- 首发不替换现有 `rules`、错误提示、提交消息体系。
- 首发不建设全站统一字段知识库。
- 首发不做中英文双语和国际化抽象。
- 首发不涉及后端接口改造。

## 3. 方案比较

### 方案 A：页面各自补提示

优点：改得快，哪里痛补哪里。  
缺点：文案和交互很快失控；同一类字段在不同页面表现不一致，维护成本高。

### 方案 B：共享聚焦说明卡组件 + 页面级字段配置（推荐）

优点：

- 交互统一，用户学习成本最低。
- 首批只覆盖高价值字段，投入可控。
- 后续可以按页面逐步扩展，不需要一次性抽象成平台级知识库。

缺点：

- 需要先建立一层组件与元数据结构。
- 首期要额外整理首批页面的字段说明文案。

### 方案 C：中心化字段知识库

优点：一致性最好，后续做国际化和 AI 辅助时复用价值高。  
缺点：前期工程量大，不符合本次“先快速解决体验断点”的目标。

结论：采用方案 B，先做统一交互壳，再按页面维护高风险字段说明。

## 4. 总体设计

整体思路是“统一交互壳 + 页面按需声明内容”，而不是把所有表单提示逻辑塞进全局样式或每个页面各写一套。

### 4.1 核心组件

#### `GuidedFormItem`

作为 `Form.Item` 的薄包装层，用于承载以下能力：

- 接受标准 `Form.Item` 属性。
- 额外接受可选的 `guide` 配置。
- 仅在 `guide` 存在时启用聚焦说明卡。
- `guide` 缺失时退回普通 `Form.Item` 行为。

边界：

- 不改变原有校验逻辑。
- 不强制全站替换所有 `Form.Item`。
- 只用于被判定为高风险说明字段的场景。

#### `FieldGuideCard`

在字段获得焦点时，显示在该字段下方的说明卡。其职责是解释“填写前的问题”，而不是承担校验职责。

固定内容结构：

- `这里填什么`
- `这个值是干嘛的`
- `推荐示例`
- `填错会怎样`

可选补充：

- `什么时候必填`
- `格式要求`

#### `FieldGuide` 元数据

页面为每个高风险字段提供一份中文说明对象，建议包含以下字段：

```ts
type FieldGuide = {
  whatToEnter: string;
  purpose: string;
  example?: string;
  impact?: string;
  whenRequired?: string;
  formatNotes?: string;
};
```

该对象只描述内容，不描述交互。交互统一由 `GuidedFormItem` 与 `FieldGuideCard` 负责。

### 4.2 页面级配置原则

首版不建立全局知识库；每个页面在本地维护自己的高风险字段说明映射，例如：

- `clusterImportGuides`
- `channelConfigGuides`
- `aiModelGuides`

这样可以保证：

- 文案离页面上下文更近，修改成本低。
- 首批可以快速打磨重点字段，不被全局抽象拖慢。
- 后续如果出现高复用字段，再考虑上提到共享词典。

## 5. 交互与数据流

### 5.1 触发方式

用户明确选择“输入框聚焦时显示”，因此本方案采用 `focus` 驱动，而不是 hover 或永久常驻。

标准行为：

1. 用户聚焦高风险字段。
2. 字段下方出现说明卡。
3. 用户失焦或切换到其他字段，当前说明卡收起。
4. 切到新的高风险字段时，显示新的说明卡。

目标效果：始终只解释用户当前正在填写的那个字段，不把整页表单变成说明书。

### 5.2 页面接入方式

页面内仅对指定字段显式声明 `guide`：

```tsx
<GuidedFormItem
  name="endpoint"
  label="API Server"
  guide={clusterImportGuides.endpoint}
  rules={[{ required: true, message: '请输入 API Server 地址' }]}
>
  <Input placeholder="https://api.k8s.example.com:6443" />
</GuidedFormItem>
```

设计约束：

- 开发者必须显式标注哪些字段进入说明体系。
- 普通字段继续保留原生 `Form.Item`。
- 不通过全局扫描或字段名猜测自动注入提示，避免不可控副作用。

### 5.3 与现有校验并行

说明卡负责“填写前解释”，现有表单规则负责“填写后纠错”：

- 聚焦说明卡：解释字段含义与填写预期。
- Ant Design `rules`：处理必填、格式错误、范围错误。
- 页面级 `message` / `notification`：处理提交成功、失败、权限、网络异常。

这三层职责不能混用，避免把说明卡做成第二套错误提示系统。

## 6. 字段筛选规则与文案模板

### 6.1 哪些字段应该进入说明卡范围

满足任一条件即可纳入：

- 字段是专业术语，新手第一次看不懂。
- 字段有隐含格式要求，单靠 label/placeholder 不够。
- 填错会导致认证失败、连接失败、配置失效、路由异常或风险升高。
- 字段值会直接影响外部系统，而不是仅影响本地展示。

典型字段：

- `endpoint`
- `kubeconfig`
- `ca_cert`
- `cert`
- `key`
- `token`
- `provider`
- `model`
- `base_url`
- `api_key`
- `configJson`
- `temperature`

不建议进入首发范围的字段：

- `name`
- `description`
- `remark`
- `enabled`
- 普通枚举、开关、备注类字段

### 6.2 文案模板

每个字段说明卡都遵循相同的文案顺序：

1. 这里填什么
2. 这个值是干嘛的
3. 推荐示例
4. 填错会怎样

可选补充：

5. 什么时候必填
6. 格式要求

这样用户只要看过一次，就知道后续所有高风险字段都按相同方式解释。

### 6.3 文案风格约束

- 不用术语解释术语。
- 优先解释业务后果，而不是解释内部实现。
- 示例必须真实、可直接照抄，不使用抽象占位符。
- 单卡信息控制在 3 到 5 行核心内容，不做滚动百科。
- 首发统一中文，不引入中英混写。

示例：

- 不推荐：`Base URL 是模型推理服务端点。`
- 推荐：`这里填模型接口地址，平台会把对话请求发送到这个地址。填错后模型连通性验证会失败。`

## 7. 首批覆盖页与字段清单

### 7.1 第一批页面

#### `ClusterImportWizard`

优先覆盖字段：

- `kubeconfig`
- `endpoint`
- `ca_cert`
- `cert`
- `key`
- `token`
- `skip_tls_verify`（如保留，需明确其安全后果）

覆盖理由：

- 这是典型的认证与连接配置表单，新手最容易在“字段用途”和“参数关系”上卡住。

#### `ChannelsConfigPage`

优先覆盖字段：

- `channelProvider`
- `channelTarget`
- `channelConfigJson`

覆盖理由：

- 渠道类型与配置内容存在强耦合；用户不知道 provider 的含义时，后续 target 与 JSON 都会连带误填。

#### `AIModelSettingsPage`

优先覆盖字段：

- `provider`
- `model`
- `base_url`
- `api_key`
- `temperature`

覆盖理由：

- 这些字段直接影响模型接入与调用质量；用户虽然可能知道“要填”，但并不一定知道“为什么这样填”。

### 7.2 第二批候选页面

- `web/src/pages/Hosts/HostOnboardingPage.tsx`
- 监控规则配置页面
- 集群详情页中的高级操作表单

第二批只在第一批模式验证有效后再推进。

## 8. 视觉、布局与可访问性

### 8.1 视觉原则

- 说明卡位于字段正下方，不采用右侧帮助面板。
- 说明卡使用当前表单视觉体系的圆角、边距和字体，不引入另一套页面语言。
- 使用轻量强调色与柔和背景区分“解释信息”与“错误信息”，避免看起来像警告框。
- 默认信息量轻，避免挤压表单主流程。

### 8.2 布局原则

- 桌面端：说明卡与字段同列显示。
- 窄屏端：说明卡自动占满字段下方宽度，不做侧栏布局。
- 说明卡不应遮挡提交按钮、弹窗底部操作区或其他字段。

### 8.3 可访问性原则

- 键盘 Tab 聚焦时同样触发说明卡。
- 说明卡出现与消失不应造成页面跳跃或焦点丢失。
- 说明内容应可被辅助技术关联到当前字段。

## 9. 异常处理与降级策略

### 9.1 降级规则

- 未配置 `guide` 的字段：按普通 `Form.Item` 渲染。
- `guide` 内容不完整：只显示已有内容，不阻断页面。
- 页面未接入 `GuidedFormItem`：功能保持原样，不引入全局副作用。

### 9.2 与错误态共存

- 校验错误继续由 Ant Design 原生错误文案承担。
- 说明卡不会替换或吞掉错误提示。
- 页面级失败消息（如网络失败、权限不足、保存失败）继续沿用现有机制。

### 9.3 内容长度控制

- 说明卡不是文档容器，不支持长篇说明或嵌套交互。
- 如某字段需要解释大量上下文，应压缩为核心短句；超出部分改为页面级帮助文档，而不是塞进说明卡。

## 10. 测试与验收

### 10.1 组件级测试

验证以下行为：

- 聚焦时显示说明卡。
- 失焦时收起说明卡。
- 普通字段不受影响。
- 缺失 `guide` 时平稳降级。
- 有校验错误时，说明卡与错误提示可以共存。

### 10.2 页面级测试

至少覆盖以下页面的关键字段：

- `ClusterImportWizard`
- `ChannelsConfigPage`
- `AIModelSettingsPage`

验证内容包括：

- 高风险字段能正确显示中文说明卡。
- 页面原有提交逻辑、校验逻辑不受影响。
- 弹窗、Drawer、Step 表单中的说明卡位置与收起行为正常。

### 10.3 验收标准

功能验收以以下结果为准：

- 第一次填写首批复杂表单的用户，基本不需要额外询问字段含义。
- 首批高风险字段的填写错误能在“提交前理解阶段”明显减少。
- 页面体验保持克制，不出现整页提示泛滥。

## 11. 分批落地策略

### Phase 1：基础能力与首批页面

- 建立 `GuidedFormItem` 与 `FieldGuideCard`
- 定义 `FieldGuide` 元数据结构
- 在 3 个代表页接入首批字段说明
- 补齐组件级与页面级测试

### Phase 2：扩展到第二批高风险表单

- 主机接入
- 监控规则
- 集群详情中的高级表单

推进前提：

- 第一批页面验证有效，且没有引入明显的视觉噪音或维护负担

### Phase 3：视效果决定是否抽共享词典

仅在以下情况下考虑：

- 多个页面出现大量重复字段说明
- 需要中英文扩展
- 需要与帮助中心、AI 辅助填写共用字段知识

在此之前，保持页面级配置，避免过早平台化。

## 12. 结论

本方案采用“共享聚焦说明卡组件 + 页面级高风险字段配置”的方式，补齐 OpsPilot 复杂表单缺失的“填写前解释层”。

关键决策如下：

- 只覆盖新手看不懂、填错代价高、专业性强的字段
- 说明只在聚焦时出现
- 首发只做中文
- 不替换现有校验和提交反馈体系
- 首批先覆盖集群导入、通知渠道、AI 模型配置三个代表页

这样可以在最小改动范围内同时追求两个结果：

- 第一次填写的人基本不用来问“这个字段是什么意思”
- 复杂表单的提交失败率明显下降
