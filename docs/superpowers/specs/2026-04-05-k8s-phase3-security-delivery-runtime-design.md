# K8s Phase 3 设计：安全与交付平台化（A -> C -> B）

## 1. 背景与决策

基于路线图 `docs/superpowers/specs/2026-04-04-k8s-management-roadmap-chart.md`，Phase 3 目标是将平台从“可操作与可治理”升级为“生产门禁级安全与交付平台”。

本次已确认的约束：

- 执行顺序：`A -> C -> B`
  - A：准入与镜像扫描门禁
  - C：GitOps + 应用市场
  - B：运行时安全治理
- 规划原则：不按固定周期拆分，以“功能完整闭环”为主。
- 验收口径：按生产门禁标准验收（多集群灰度、SLO/SLA、灾备演练、值班 Runbook 全套）。

## 2. 总体目标与范围

### 2.1 总体目标

1. 建立从镜像供应链到集群准入的安全门禁闭环。
2. 建立从应用模板到多环境发布的标准化交付闭环。
3. 建立从运行时检测到自动处置与复盘的安全运营闭环。
4. 统一审计、回滚、告警与演练体系，满足生产门禁要求。

### 2.2 范围

- In Scope：
  - 准入与镜像扫描门禁（A）
  - GitOps 与应用市场标准化（C）
  - 运行时安全检测与处置（B）
  - 跨域治理（审计、SLO/SLA、演练、Runbook）
- Out of Scope：
  - 业务侧自定义安全编排 DSL（留待后续迭代）
  - 跨组织多控制面联邦治理（留待后续迭代）

## 3. 技术栈与架构选择

采用已确认方案（A 方案）：

- A（准入与镜像）：`OPA Gatekeeper + Trivy + Kyverno(可选策略包)`
- C（交付与市场）：`ArgoCD + Harbor(Helm OCI)`
- B（运行时安全）：`Falco + Tetragon`

选择理由：

1. 组件成熟、生态完整，支持生产场景可观测与可审计。
2. 与现有“审批/审计/操作中心”治理体系耦合成本低。
3. 可以形成“准入前防护 + 运行中检测 + 交付链约束”的闭环。

## 4. 路线与任务结构（A -> C -> B）

### 4.1 P3-A：准入与镜像扫描门禁

1. A1：镜像供应链基线
  - Harbor 项目分级
  - 镜像签名策略
  - SBOM 与漏洞元数据落库
2. A2：Trivy 扫描门禁
  - 漏洞分级阈值（Critical/High 等）
  - 扫描结果可检索、可追溯
3. A3：Admission 策略包
  - Gatekeeper/Kyverno 策略模板
  - 策略版本化与回滚
4. A4：例外机制
  - namespace/workload 维度时效豁免
  - 审批、过期自动回收、审计记录
5. A5：多集群一致性
  - 策略分发、版本比对、一致性校验
  - 失败回滚与告警

### 4.2 P3-C：GitOps + 应用市场

1. C1：ArgoCD 多集群接管
  - Project/RBAC 隔离
  - Sync Waves 与健康检查
2. C2：应用市场
  - Harbor Helm OCI 仓库
  - 模板门禁（schema/lint/安全基线）
3. C3：环境晋级发布
  - DEV -> STG -> PROD promotion
  - 审批卡点与变更单联动
4. C4：漂移治理
  - 漂移检测、冲突提示、自动修复策略
5. C5：回滚与熔断
  - 版本回滚、配置回滚
  - 发布失败自动熔断

### 4.3 P3-B：运行时安全治理

1. B1：运行时检测基线
  - Falco/Tetragon 规则分层（基础/加强/业务特化）
2. B2：告警与处置
  - 告警分级
  - 自动隔离/阻断 + 人工确认流程
3. B3：事件取证
  - 进程、网络、容器元数据快照
  - 证据留存与审计关联
4. B4：运营闭环
  - 误报治理
  - 规则灰度、命中率与噪声比看板
5. B5：策略反哺
  - 将运行时事件反哺到准入策略与发布策略

### 4.4 跨域治理任务（贯穿 A/C/B）

1. G1：统一审计模型
2. G2：SLO/SLA 与告警分级体系
3. G3：多集群灰度与灾备演练剧本
4. G4：值班 Runbook 与升级/降级手册

## 5. 关键依赖关系

1. `A -> C/B`：准入门禁是交付与运行时安全的前置约束。
2. `C -> B`：GitOps 提供标准变更基线，便于运行时事件归因。
3. `B -> A/C`：运行时事件反哺准入策略与发布策略，形成闭环优化。

## 6. 生产门禁级验收标准（DoD）

### 6.1 A（准入与镜像）DoD

1. Critical 漏洞镜像在生产环境默认不可发布。
2. 未签名或签名不可信镜像默认拦截。
3. 准入拒绝可解释（策略名、命中规则、修复建议）。
4. 例外必须审批、可追踪、可过期回收。
5. 多集群策略一致性校验与回滚能力可用。

### 6.2 C（GitOps + 应用市场）DoD

1. 生产发布仅允许 GitOps 路径。
2. 应用模板需通过 schema/lint/安全基线门禁后上架。
3. 支持分环境晋级与审批卡点。
4. 发布失败自动熔断并支持一键回滚。
5. 漂移可检测并可配置自动修复。

### 6.3 B（运行时安全）DoD

1. 高危行为可检测并分级告警。
2. 告警可关联集群/命名空间/工作负载/发布版本。
3. 自动处置动作可审计。
4. 具备误报治理机制（规则灰度、白名单、回归验证）。
5. 事件取证与复盘可沉淀 Runbook。

### 6.4 跨域上线门槛

1. 多集群灰度演练记录完整。
2. 关键 SLO/SLA 达标并持续可观测。
3. 灾备演练可复现（准入、交付、运行时三链路）。
4. 值班 Runbook 与升级/降级手册齐备。

## 7. 风险与控制

1. 风险：策略过严导致交付受阻  
   控制：灰度策略、例外审批、时效豁免、回滚策略版本。
2. 风险：运行时告警噪声过高  
   控制：规则分层、基线学习、误报治理与阈值调优。
3. 风险：多集群策略漂移  
   控制：统一版本源、漂移告警、自动修复与定期巡检。
4. 风险：GitOps 与人工操作冲突  
   控制：生产仅 GitOps 入口、越权操作审计与告警。
